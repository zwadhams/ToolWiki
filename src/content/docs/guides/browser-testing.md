[Playwright](../../tools/playwright/) checks browser behavior against assertions
you write. [axe-core](../../tools/axe-core/) evaluates automated accessibility
rules in a rendered page state. This example gives each tool a separate fault
to detect in a small search page.

The [example files](https://github.com/zwadhams/ToolWiki/tree/main/examples/browser-testing)
are separate from the live ToolWiki application. The fixture binds only to
`127.0.0.1:8837`, uses no credentials, and has no external services. Its links
point to ToolWiki profiles, but the tests check their destinations without
navigating to them.

## Prepare the isolated example

[Get the repository examples](../get-examples/), then use Node.js 24 and
pnpm 11.25.0. From the repository root:

```sh
cd examples/browser-testing
pnpm install --ignore-workspace --frozen-lockfile
pnpm run install:browser
```

The install command uses this example's lockfile. The browser script downloads
the Chromium build expected by Playwright into this example's `.browsers/`
directory. It does not replace the browser you use for normal browsing. On
Linux, [Playwright's browser dependencies](https://playwright.dev/docs/browsers#install-system-dependencies)
may also need to be installed for your distribution.

The recorded execution used Node.js 24.22.1, Playwright Test 1.65.0,
`@axe-core/playwright` and axe-core 4.14.0, and Chromium 158.0.8127.18 on a Windows
ARM64 host. The downloaded browser was the win64 distribution. Other supported
hosts are documented upstream but were not run for this example.

## Reproduce both faults

Run the unchanged tests against the faulty page:

```sh
pnpm test:bad
```

Expect exit status 1 and two failing tests:

| Check | Observed failure | Meaning |
| --- | --- | --- |
| Capability search | The `memory` query left zero visible results where one was expected. | The faulty filter examines tool names but omits capability text. |
| Initial-page axe scan | Rule `label` identified `#tool-query`. | The input lacked an accessible name in this rendered page. |

The runner starts and stops its own local server. If port 8837 is already in
use, it refuses to reuse that service. A missing browser, server failure, timeout,
or other infrastructure error is not evidence that either intended fault was
detected.

Full test output and axe attachments are written to `.results/bad/report.json`.
The failure screenshots and error context are under `.results/bad/artifacts/`.
These files are regenerated by later runs of the same variant.

## Apply the corrections and repeat

The corrected page makes two small changes: it searches the visible tool and
capability text, and it adds an explicit label associated with the search input.
Run the same test file against that version:

```sh
pnpm test:good
```

Expect exit status 0 and two passing tests. In the recorded run, `memory`
retained the AddressSanitizer result and its profile URL, and a case-insensitive
name query retained mypy. The initial-page axe scan had no violations or
incomplete results for the selected rule tags.

To verify the complete before-and-after exercise and create a compact record:

```sh
pnpm verify
```

The verifier requires exactly the two intended failures on the faulty page and
two passes on the corrected page. It checks that a browser actually started,
that the capability failure was the result-count assertion, and that axe
reported `label` for the faulty page. It writes `.results/verification.json`
with versions, commands, process statuses, input hashes, and rule-result IDs.
The [retained execution](https://github.com/zwadhams/ToolWiki/blob/main/audits/browser-testing/record.json)
and [audit notes](https://github.com/zwadhams/ToolWiki/blob/main/audits/browser-testing/README.md)
describe the run used by this guide.

## Understand the tested scope

The behavior test checks a small search contract at one viewport. It does not
exercise every query, browser, device, navigation route, or interaction. The
accessibility test scans the initial page with `wcag2a`, `wcag2aa`, `wcag21a`,
and `wcag21aa` tags. It does not scan the filtered states from the behavior test.

A scan without violations is not a full accessibility assessment. Inspect any
`incomplete` results, exercise additional states, and include manual keyboard,
screen-reader, zoom, and user assessment for the real application.
[Playwright's accessibility guide](https://playwright.dev/docs/accessibility-testing)
explains these limits and the axe integration.

## Adapt this to an existing application

Keep the project's browser configuration, locked tool versions, test projects,
and test-data reset procedure. Use a browser-renderable test UI, then write
assertions for the visible outcomes users need. The system builder's
**Browser UI** technology describes this requirement; a running backend or
command-line process alone does not satisfy it.

Prefer [role and label locators](https://playwright.dev/docs/locators) where they
represent the application's user-facing contract. This example uses a test ID
to reach the deliberately unlabeled input so the behavior and accessibility
failures remain independent. That test ID does not supply an accessible name.

Retain the application revision, browser build, viewport, selected states,
assertions, axe version, and rule tags in a [run record](../run-record/). Keep
assertion failures and incomplete execution distinct when deciding how to
[handle checks in CI](../ci-checks/).
