## Where it fits

AddressSanitizer adds a memory-error detector to executions generated by tests or fuzzers. It pairs naturally with [AFL++](../afl-plus-plus/) or [libFuzzer](../libfuzzer/).

## First try

**Illustrative example, not run here.** With Clang and its sanitizer runtime installed on a supported host, save `bounds.c`:

```c
#include <stdlib.h>
int main(void) {
    int *values = malloc(2 * sizeof(*values));
    if (!values) return 1;
    values[2] = 7;
    free(values);
    return 0;
}
```

Build and run this small test in a Unix-style shell on a supported host:

```sh
clang -O0 -g -fsanitize=address -fno-omit-frame-pointer bounds.c -o bounds
./bounds
```

For Windows PowerShell, use a compiler environment with `clang`, its C linker/libraries, and the matching AddressSanitizer runtime available. This uses the `clang` driver, not `clang-cl`; these commands are also illustrative and have not been run here:

```powershell
clang -O0 -g -fsanitize=address -fno-omit-frame-pointer bounds.c -o bounds.exe
.\bounds.exe
```

Before choosing this route, confirm the compiler target and runtime match your executable's architecture. A Windows label alone does not establish that your toolchain or dependencies are compatible.

Representative report outline, not captured output; addresses and most stack frames are omitted:

```text
ERROR: AddressSanitizer: heap-buffer-overflow
WRITE of size 4
    #0 main ... bounds.c:5
... allocated ...
    #0 ... malloc ...
    #1 main ... bounds.c:3
```

The error names the kind of invalid access. The first stack points to the write, and the allocation stack points to the two-element allocation. Index 2 is outside that allocation; valid indices are 0 and 1. Correct the index and repeat. The report format and symbol locations depend on the platform and available debug information.

For toolchain installation and platform-specific setup, use the [Clang AddressSanitizer guide](https://clang.llvm.org/docs/AddressSanitizer.html).

## Interpret coverage

A successful execution only covers the behavior that ran. Keep the build flags, workload, and suppression settings with the report.

See [memory-error detection](../../guides/memory-error-detection/) to compare an instrumented build with static checking and Memcheck's executable instrumentation.

If you only have an existing executable, check [Memcheck](../valgrind-memcheck/) or [Dr. Memory](../dr-memory/) for a compatible host and binary. They use different runtime checking workflows; check the platform limits before choosing one.
