## First try

Use the repository's
[`examples/http-api`](https://github.com/zwadhams/ToolWiki/tree/main/examples/http-api)
fixture and k6 1.0.0. The [local API guide](../../guides/api-testing/)
describes its loopback service. From the fixture directory, start the corrected
service in one terminal:

```sh
python server.py --fixed
```

In another terminal in that directory, run the supplied script:

```sh
k6 run --no-usage-report load.js
```

The script accepts only an IPv4 loopback URL. Its default endpoint is
`http://127.0.0.1:8771/health`; `BASE_URL` can select another loopback port.
Setup requires the fixture's `ready` status and `fixed` mode before starting
load. This read-only endpoint needs no authentication, test data, or reset.
Stop the server with Ctrl+C afterward.

The workload uses two virtual users for ten seconds, with a half-second pause
after each request. This is a closed model: slower iterations reduce the arrival
rate. It is not a fixed requests-per-second target. Each load request has a
two-second timeout and the scenario allows two seconds to finish at the end.

The selected criteria are all response checks passing, no failed HTTP requests,
and the 95th-percentile load-request duration below 500 ms. These are tutorial
thresholds, not a service-level objective for your project. The script saves
`k6-summary.json`; preserve it under a new name before another run.

## Separate checks, thresholds, and completion

Checks record Boolean outcomes. Without a corresponding threshold, failed
checks do not make the whole run fail. Inspect the process status, completed
iterations, and threshold results together. If setup fails before load, empty
metrics or apparently passing thresholds are not a successful measurement.

**Executed on Windows with k6 1.0.0 against the local fixture.** A run completed
40 load iterations with its thresholds met. A deliberately impossible latency
threshold failed while response checks passed. The faulty-mode service failed
setup before load. These are checks of the recipe and status handling, not
service-capacity measurements. The
[execution record](https://github.com/zwadhams/ToolWiki/blob/main/audits/remaining-work/executions/k6/record.json)
retains input hashes, commands, endpoint ports, and process statuses beside the
captured summaries.

## Adapt the workload

Record the target revision, service settings, generator host, competing activity,
network path, duration, arrival model, and thresholds in a
[run record](../../guides/run-record/). Prepare reset and cleanup before testing
operations that change data. Use the load model appropriate to the intended
demand and check that the generator can produce it.

[Schemathesis](../schemathesis/) generates schema-based requests;
[RESTler](../restler/) explores stateful API sequences. k6 evaluates your chosen
workload and thresholds. These tools answer different questions.
